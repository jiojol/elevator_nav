# 批量仿真占用冲突修正 · 2026-10-28

用户两次批量任务的 `native_straight/console.log` 都记录“已有本机仿真在运行，请等它结束”。
当时 20:01:17 启动的楼梯单项仍在运行，约 70 秒后结束；批量启动发生在 20:01:26 和 20:02:07，均与它重叠。
原因是运行入口占用冲突，之前的批量入口又把具体错误隐藏在日志中，只输出 `harness_error`。

修正内容：

- 批量任务默认最多等待 180 秒，显示占用场景、PID 和输出目录，释放后自动继续。
- 锁信息只在成功取得锁后更新，竞争任务不会清空正在运行者的信息。只有锁文件而没有活动锁时不阻止启动。
- 终端实时显示进度和实际错误，同时保存日志；占用超时记为 `busy`，其他启动失败记为 `startup_error` 并附具体原因。
- 批量任务中断时发送一次 SIGINT，允许子进程清理自己启动的本机 ROS 节点；单独的子进程会话避免终端同时发送两次中断。
- 子进程没有生成结果时不能以零退出码当作执行成功。

验证：5 项排队、占用信息保持、错误显示、失败分类和中断清理检查通过；原 3 项本机入口约束检查通过。
另用短时占用进程触发真实排队，随后按完整批量入口运行 9 项场景，9 项均生成结果，批量进程退出码为 0。
本轮没有远端连接，也未修改导航算法或部署到机器狗。

[本轮结果和排队输出](queue_fix_results.json)。有 3 项到达、3 项超时、2 项失稳、1 项恢复次数用尽。
这里验证的是批量入口正常执行与正确报告结果，不能把真实导航失败算成通过。

复现命令：

```bash
python3 simulation/run_matrix.py \
  --output "simulation/artifacts/my_matrix_$(date +%Y%m%d_%H%M%S)"
```

无需手动删除锁文件或杀死其他任务。已有仿真时会自动显示等待。
